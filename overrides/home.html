The problem

You've said it before.
It's on disk.

You correct Claude for the same things across repos and weeks: test style, lockfile edits, naming conventions. Each correction costs a turn and some attention, and every one of them is already written down in your session transcripts. Nobody reads them.

sminer reads them. It finds the pushback, interrupts, rewinds and repeated instructions, groups them by the rule underneath, and ranks them by how often they happen and across how many repos.

From friction to fix

The right remedy for each rule.
Deterministic beats instructed.

When a rule can be checked mechanically, sminer proposes a hook. When it needs judgment, a CLAUDE.md line. When you keep re-explaining a procedure, a skill. Anything you already have is left out.

Hook

a file path or a command can enforce it

A PreToolUse script for your hooks directory, plus the settings.json entry that registers it.

if grep -Eq '(^|/)package-lock\.json$'; then
  echo 'Blocked: run npm install' >&2
  exit 2
fi

CLAUDE.md line

judgment or style the model must apply

A diff appending the rule to the repo's CLAUDE.md, or the global one when it spans repos.

 ## Learned conventions

+- Write table-driven tests with the
+  standard library, not testify.

Skill

a procedure you keep re-explaining

A draft SKILL.md with the steps you typed out in session after session, ready to edit.

Why sminer

Guardrails from evidence,
not from memory.

{% include ".icons/material/magnify-scan.svg" %}

Seven kinds of friction

Corrections, interrupts, rejected tool calls, rewinds, repeated instructions, hook blocks, failure loops and manual fix-ups. Cheap heuristics first; the model only confirms candidates.

{% include ".icons/material/shield-lock-outline.svg" %}

Private by default

Secrets are redacted before anything is stored, and transcripts are never copied. --offline keeps everything local; otherwise only about 2 KB per candidate goes to the classifier.

{% include ".icons/material/lightning-bolt.svg" %}

Fast and incremental

Each run reads only what's new since the last one. Ninety days of transcripts take well under thirty seconds on a laptop; a repeat run takes a few.

{% include ".icons/material/file-document-edit-outline.svg" %}

Proposals, not edits

Accepting a finding writes a patch file. You review it and apply it. sminer never touches your CLAUDE.md, settings or hooks.

{% include ".icons/material/chart-line.svg" %}

Proof the fix worked

sminer finding trend splits each finding's weekly rate at the day you adopted the fix, so you can see the correction stop happening.

{% include ".icons/material/code-json.svg" %}

Made for scripts too

--json on every command, data on stdout and logs on stderr, documented exit codes, and shell completion of live finding IDs.

Quick start

From transcripts to a fix
in four commands.

sminer is a single Go binary with no cgo and no setup: it finds Claude Code's transcripts in ~/.claude/projects on its own. Start offline, then add an API key for sharper results.

{% include ".icons/material/book-open-page-variant-outline.svg" %} Full getting-started guide

  1. Install

    $ {{ install }}

  2. Mine your transcripts, offline

    Nothing leaves your machine. The report goes to stdout, or a file with -o.

    $ sminer run --offline -o report.md

  3. Optional: let the model confirm candidates

    $ export ANTHROPIC_API_KEY=...
$ sminer run -o report.md

  4. Preview a fix, then accept it

    $ sminer finding accept Fc72cc0 --preview
$ sminer finding accept Fc72cc0   # prints the patch path

How it works

A batch pipeline on your machine.
One optional network call.

Each stage reads from and writes to a local SQLite file, so any stage can be re-run on its own. Only the classifier leaves the machine, and --offline turns it off.
